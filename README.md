# Этап 0 — eGov Mobile QR Vote

Минимальный тестовый стенд для проверки авторизации и подписания документа через **eGov Mobile QR** (API SIGEX).

Реализует техническое задание `docs/ТехЗадание_Этап_0.txt`:

1. **Кнопка № 1 — авторизация.** Приложение создаёт сессию в SIGEX, показывает QR-код. После сканирования и подтверждения в eGov Mobile сервер получает CMS-подпись, извлекает из сертификата подтверждённые ФИО и ИИН.
2. **Кнопка № 2 — подписание тестового голоса.** Сервер формирует JSON-документ бюллетеня, отправляет его на подпись через eGov Mobile QR, сохраняет исходный документ и CMS-подпись, выполняет криптографическую проверку.

## Как это работает

```
Браузер            Приложение (FastAPI)              SIGEX                    eGov Mobile
   │  POST /api/auth/init │                            │                          │
   │─────────────────────>│  POST /api/egovQr          │                          │
   │                      │───────────────────────────>│                          │
   │  QR (PNG base64)     │<── qrCode, dataURL, signURL│                          │
   │<─────────────────────│                            │                          │
   │                      │  POST dataURL (фон)        │                          │
   │                      │───────────────────────────>│  данные ждут сканирования│
   │  опрос статуса       │                            │<─────────────────────────│
   │─────────────────────>│                            │  GET dataURL             │
   │                      │  GET signURL (фон)         │─────────────────────────>│
   │                      │───────────────────────────>│  пользователь подписал   │
   │                      │<── CMS PKCS#7 ─────────────│<─────────────────────────│
   │  completed + ФИО/ИИН │  разбор и проверка ЭЦП     │                          │
   │<─────────────────────│                            │                          │
```

Ключевые особенности реализации:

- запросы `POST dataURL` и `GET signURL` в SIGEX **блокируются до действий пользователя**, поэтому выполняются в фоновой задаче, а не в HTTP-обработчике;
- `qrCode` от SIGEX — это готовое PNG-изображение в base64, поэтому в интерфейсе используется `<img src="data:image/png;base64,...">`;
- браузер опрашивает только локальный эндпоинт `/api/sessions/{id}` раз в 2 секунды;
- фоновая задача ограничена сроком действия QR (`expireAt` + 2 минуты).

## HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/` | Веб-интерфейс |
| `GET` | `/api/health` | Проверка работоспособности |
| `POST` | `/api/auth/init` | Создать QR для авторизации |
| `POST` | `/api/sign/init` | Создать документ и QR для подписи |
| `GET` | `/api/sessions/{id}` | Статус сессии |

Статусы сессии: `pending` → `data_sent` → `completed`, либо `canceled`, `expired`, `error`.

## Документ бюллетеня

Формируется строго по ТЗ:

```json
{
  "poll_name": "Тестовое голосование № 1",
  "question": "Согласны ли вы с предложенным решением?",
  "answer": "За",
  "user_fullname": "<ФИО>",
  "doc_id": "<UUIDv4>",
  "created_at": "<ISO-8601>"
}
```

После подписания в `data/vote/` сохраняются:

- `<дата>_<doc_id>.json` — документ, base64 подписи, результат проверки, данные подписанта;
- `<дата>_<doc_id>.cms` — CMS-подпись в DER.

## Проверка ЭЦП

Локальная проверка (`verify_cms` в `App/main.py`) выполняет:

1. разбор CMS SignedData и поиск сертификата подписанта;
2. сверку `messageDigest` из подписанных атрибутов с хешем исходного документа;
3. проверку подписи открытым ключом сертификата (RSA PKCS#1 v1.5 и RSA-PSS);
4. проверку срока действия сертификата;
5. извлечение ФИО (`CN`) и ИИН/БИН (`SERIALNUMBER`) из сертификата.

**Ограничение Этапа 0:** локально поддерживаются подписи RSA. Для сертификатов ГОСТ (НУЦ РК, юридические лица) сертификат и подписант разбираются, но криптографическая проверка ГОСТ не выполняется — требуется проверка через SIGEX/НУЦ РК. Это отражается в интерфейсе как «проверка ограничена».

## Журнал

Все события пишутся в `data/logs/app.log` (ротация: 5 МБ × 5 файлов). В консоль также выводится информация о старте, создании сессий, передаче данных и результате проверки.

## Ограничения стенда

- сессии хранятся в памяти процесса; после перезапуска незавершённые сессии теряются;
- Это демонстрационный стенд Этапа 0, а не промышленная система голосования: нет аутентификации администратора, БД, защиты от повторной подписи и т. п.
